I wrote that the spec asserted "genuine streaming, not just final state" because labels were checked before `waitForFinish`. That inference was invalid. ### The fix — correct, minimal, right abstraction

`composer/index.tsx:1459` swaps `setUserInput` → `replaceUserInput`. The two are not interchangeable:

- `setUserInput = onChangeText` (`:1233`) is the input's *change handler*, wired at `:2360`. Called programmatically it updates draft state only — the uncontrolled input keeps rendering stale text, which is exactly the dropped-mention symptom.
- `replaceUserInput` (`:1297-1306`) routes through `messageInputRef.current.replaceText(...)`, and `input/input.tsx:1247-1258` writes the DOM value, sets `selectionRef` to end-of-text, *and* calls `onChangeText` itself.

So the fix restores DOM and state together; the old call did state only. I checked the caret specifically, since the call passes no `selection` while `setCursorIndex(nextInput.length)` remains: `replaceText` defaults to `{ start: nextText.length, end: nextText.length }` (`:1252`), so the real caret and `cursorIndex` agree. No disagreement introduced.

On simplicity — this reuses the existing setter rather than adding a wrapper, matching all six other programmatic mutations (`:1318`, `:1347`, `:1568`, `:1879`) and the `setUserInput: replaceUserInput` aliasing already handed to children at `:1367` and `:1610`. It aligns with the established contract instead of inventing one, per plan rule 2. The dependency array is updated correspondingly and `replaceUserInput` is a stable `useCallback`.

Security: no new surface. The setter choice doesn't touch path resolution or scheme handling; dropped paths still flow through the existing workspace-constrained mention path.
